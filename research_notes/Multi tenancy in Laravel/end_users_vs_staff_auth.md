# Authenticating tenant end-users (chatters) separately from tenant staff in Laravel

Scope note for the report writer. Framework behaviour below was checked against the code installed in this repo (`vendor/composer/installed.json`): laravel/framework v13.35.0, laravel/fortify v1.41.0, laravel/sanctum v4.3.3, filament/filament v5.10.1, laravel/socialite v5.31.0, laravel/passkeys v0.2.1. The GitHub links point to the upstream branch of each file. Line numbers can drift between releases, but the logic quoted here matches the installed copies. Facts about Chatvia itself cite repo paths (local, not URLs).

Current Chatvia baseline (local repo facts, for context):
- `users.email` is `->nullable()->unique()`: one global identity space for admins, owners, teammates and chatters. Source: `database/migrations/0001_01_01_000000_create_users_table.php` (local).
- `password_reset_tokens.email` is the primary key (the stock Laravel 11+ skeleton layout). Source: same migration (local); upstream skeleton [laravel/laravel create_users_table](https://github.com/laravel/laravel/blob/13.x/database/migrations/0001_01_01_000000_create_users_table.php).
- `config/auth.php` already has three session guards on the **same** `users` provider: `web` (dashboard), `chat` (hosted chat, "its own sign-in on its own session cookie (session.chat)"), and `admin` (Filament). Source: `config/auth.php` (local).
- `UseHostedChatSession` is global middleware. It switches `session.cookie`/`session.path`/`same_site` for `/chat/` requests before the `web` group starts the session, so the chat session is separate from the dashboard session. Source: `src/App/Http/Middleware/Chat/UseHostedChatSession.php`, `config/session.php` (`'chat' => [... 'path' => '/chat']`, `partitioned`) (local).
- `fortify.guard = 'web'`, `fortify.passwords = 'users'`, `sanctum.guard = ['web']`. Source: `config/fortify.php`, `config/sanctum.php` (local).

So Chatvia already has **session isolation**. What it lacks is **identity isolation**: the same email cannot be a chatter in two workspaces, because a chatter is a row in the global `users` table.

## 1. Multiple authenticatable models (separate guards + providers) vs one `users` table with a type column

### Takeaway
Laravel supports several authenticatable models out of the box. A **guard** decides *how* a request is authenticated. A **provider** decides *where* the user row comes from. Each password **broker** names its own provider. Large e-commerce codebases use a separate `Customer` model, guard and broker next to the staff model. Forum advice that favours "one users table + roles" is about staff *roles*, not about separate identity spaces. When end-users need their own per-tenant identity (the same email under two tenants), a separate model/table, or a single table with scoped providers, is the Laravel-native route.

### Cited Findings
- Laravel docs: "Guards define how users are authenticated for each request… Providers define how users are retrieved from your persistent storage… you are free to define additional providers as needed." — [Laravel 13 Authentication](https://laravel.com/docs/13.x/authentication#introduction)
- Laravel docs, "Accessing Specific Guard Instances": `Auth::guard('admin')->attempt($credentials)` "allows you to manage authentication for separate parts of your application using entirely separate authenticatable models or user tables." — [Laravel 13 Authentication](https://laravel.com/docs/13.x/authentication#accessing-specific-guard-instances)
- `PasswordBrokerManager::resolve()` builds each broker with `$this->app['auth']->createUserProvider($config['provider'] ?? null)`. Every broker in `auth.passwords` is therefore bound to one named provider, and so to one model/table. — [PasswordBrokerManager.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/PasswordBrokerManager.php)
- Real-world example: Bagisto (Laravel e-commerce) defines a `customer` session guard → `customers` provider → `Customer` model → `customers` table, and an `admin` guard → `admins` provider → `Admin` model → `admins` table. Its summary: "Two guards, two providers, two models, two tables, two reset flows." (Article dated 23 July 2026.) — [Bagisto multi-guard authentication](https://bagisto.com/en/bagisto-multi-guard-authentication/)
- Community counter-advice. Laracasts threads lean toward one `users` table plus roles/authorization for *different roles of the same population*, and argue guards are for different auth *methods*. Undated or older forum content. — [Laracasts: multiple guards or permissions](https://laracasts.com/discuss/channels/site-improvements/architecture-question-multiple-guards-or-permissions); [Laracasts: admin users separate table vs single table](https://laracasts.com/discuss/channels/laravel/admin-users-separate-table-vs-single-table)
- A 2020 laravel/framework discussion about logging in as admin and customer at once got the suggestion of a single table with a user-level column. Older; read through a search summary, not fetched in full. — [laravel/framework Discussion #34401](https://github.com/laravel/framework/discussions/34401)
- Cost of multiple guards with spatie/laravel-permission: each guard is its own namespace, so permissions and roles must be created per guard. The page found is the older v3 docs. — [spatie/laravel-permission: multiple guards](https://spatie.be/docs/laravel-permission/v3/basic-usage/multiple-guards)
- Single-table inheritance option. `tightenco/parental`: the parent uses `HasChildren`, each child uses `HasParent` and reads the parent's table. `$childTypes` maps short aliases (for example `'admin' => Admin::class`) so class names stay out of the DB. `$childColumn` overrides the default `type` column. The README does not mention authentication or auth providers. — [tighten/parental README](https://github.com/tighten/parental)
- `calebporzio/parental` is abandoned; its author points to `tightenco/parental`. — [Packagist calebporzio/parental](https://packagist.org/packages/calebporzio/parental)
- `EloquentUserProvider::newModelQuery()` builds the query through `$model->newQuery()`, so the model's global scopes apply. The provider also has a public `withQuery(Closure $queryCallback)` hook that is applied to every lookup. A provider can therefore be restricted, for example to `type = 'chatter'`, without changing the model. — [EloquentUserProvider.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/EloquentUserProvider.php)

### Inferences
- Three Laravel-native shapes fit Chatvia's problem:
  1. **Separate model and table.** A `Chatter` model on a `chatters` table, with `workspace_id` (the owner's `users.id`), `email`, `password`, a `chatters` provider, guards `chat` (session) and optionally `chatter-api` (sanctum), and a `chatters` password broker. This gives the cleanest identity space: staff tooling (Fortify, Filament, Sanctum's `users` provider) never sees chatter rows, and `unique(workspace_id, email)` is a plain composite index. It costs a model move: `Membership\Agent` pivots (`agent_user`), conversations, `message_limits` for a chatter, morph aliases and analytics that point at `users.id` for chatters must be re-pointed. CLAUDE.md lists models and morph aliases under "never rename/move without a plan".
  2. **Same table with scoped providers.** Keep `users`, add `workspace_id` (null for staff), and replace the global unique index with two partial unique indexes (section 2). Then give each guard its own provider that filters by type: `Auth::provider('staff', …)` / `Auth::provider('chatters', …)` returning `EloquentUserProvider` with `withQuery()`, or Parental child models (`Staff`, `Chatter`) as provider models. This is a smaller migration, but **every** lookup path must be scoped (Fortify login, Fortify reset, Filament, Sanctum, Socialite, `Rule::unique`, `exists`). One missed path returns an arbitrary row, because `retrieveByCredentials()` ends in `->first()` (section 2).
  3. **One global identity plus per-tenant membership.** This is roughly today's design: one row per email, `agent_user` as the pivot. It cannot give the same person *separate* credentials per tenant, which is the stated goal, so it does not solve the problem.
- Illustrative config for shape 1. This is not taken from a source. It applies the documented guard/provider/broker structure:

```php
// config/auth.php
'guards' => [
    'web'   => ['driver' => 'session', 'provider' => 'users'],    // dashboard (Fortify)
    'admin' => ['driver' => 'session', 'provider' => 'users'],    // Filament
    'chat'  => ['driver' => 'session', 'provider' => 'chatters'], // hosted chat
    'sanctum' => ['driver' => 'sanctum', 'provider' => 'users'],  // pin /api/v1 to staff (section 4)
],
'providers' => [
    'users'    => ['driver' => 'eloquent', 'model' => App\Identity\…\User::class],
    'chatters' => ['driver' => 'eloquent', 'model' => App\Identity\…\Chatter::class],
],
'passwords' => [
    'users'    => ['provider' => 'users',    'table' => 'password_reset_tokens', 'expire' => 60, 'throttle' => 60],
    'chatters' => ['provider' => 'chatters', 'table' => 'chatter_password_reset_tokens', 'expire' => 60, 'throttle' => 60],
],
```

- I found no survey data on *how common* separate customer models are in Laravel SaaS. The evidence is anecdotal: Bagisto, tutorials, and forum threads.
- I could not confirm from the Parental README whether querying a child model (`Chatter::where(...)`) adds a global `type` scope automatically. I believe `HasParent` does, but did not verify it in source. Test before relying on Parental children as auth provider models.
- The Laravel Daily video on "multiple guards vs roles" mentioned in forum posts was not found.

## 2. Tenant-scoped email uniqueness and how sign-in finds the right row

### Takeaway
Uniqueness becomes a composite `(tenant_id, email)` index. On PostgreSQL, a single table needs *partial* unique indexes (staff global, chatters per workspace), and Laravel's Blueprint cannot express those, so they need `DB::statement`. Sign-in finds the right row only if the tenant key is passed as an extra credential. `EloquentUserProvider::retrieveByCredentials()` turns every non-password key into a `where` and returns `->first()`. Validation rules (`Rule::unique`, `Rule::exists`) run plain queries and must be scoped by hand.

### Cited Findings
- `retrieveByCredentials()` removes every key whose name *contains* `password`, then: array/Arrayable values become `whereIn`, closures are called with the query, and other values become `where($key, $value)`. It returns `$query->first()`. — [EloquentUserProvider.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/EloquentUserProvider.php)
- Docs, "Specifying Additional Conditions": "you may also add extra query conditions to the authentication query… `Auth::attempt(['email' => $email, 'password' => $password, 'active' => 1])`". For complex conditions, a closure in the credentials array: `fn (Builder $query) => $query->has('activeSubscription')`. `attemptWhen($credentials, fn (User $user) => …)` inspects the found user before login. — [Laravel 13 Authentication](https://laravel.com/docs/13.x/authentication#specifying-additional-conditions)
- Login throttling in the starter kits / Fortify "is unique to the user's username / email address and their IP address". — [Laravel 13 Authentication](https://laravel.com/docs/13.x/authentication#login-throttling)
- stancl/tenancy v4 single-database docs: to scope UNIQUE indexes, change `$table->unique('slug')` to `$table->unique(['tenant_id', 'slug'])`. Laravel validation rules "run plain queries rather than models", so they must be scoped manually: `Rule::unique('posts', 'slug')->where('tenant_id', tenant('id'))`. `HasScopedValidationRules` adds `$tenant->unique('posts')` / `$tenant->exists('posts')`. `DB` facade queries are not scoped. — [Tenancy for Laravel v4: single-database tenancy](https://v4.tenancyforlaravel.com/single-database-tenancy/) (v3 equivalent: [v3 single-database tenancy](https://tenancyforlaravel.com/docs/v3/single-database-tenancy/))
- The tenancy v4 single-DB page has **no** guidance on users, login, password resets or per-tenant authentication. — [Tenancy for Laravel v4: single-database tenancy](https://v4.tenancyforlaravel.com/single-database-tenancy/)
- PostgreSQL partial unique index (PG 18 docs, Example 11.3): `CREATE UNIQUE INDEX tests_success_constraint ON tests (subject, target) WHERE success;` "enforces uniqueness among the rows that satisfy the index predicate, without constraining those that do not." — [PostgreSQL 18: Partial Indexes](https://www.postgresql.org/docs/current/indexes-partial.html)
- Laravel's index definition supports Postgres `nullsNotDistinct()`, `deferrable()`, `algorithm()`, `online()` and others, but has **no** `where`/partial-predicate option. A partial unique index needs a raw statement. — [IndexDefinition.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Database/Schema/IndexDefinition.php); [PostgresGrammar.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Database/Schema/Grammars/PostgresGrammar.php)
- `Rule::unique()` / `Rule::exists()` extend `DatabaseRule`, which exposes `where($column, $value = null)` for extra constraints. — [DatabaseRule.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Validation/Rules/DatabaseRule.php)
- A community schema for a shared users table uses a composite `unique_email_per_tenant` key on `(tenant_id, email)`. This is a generic blog example. — [DEV: multi-tenant SaaS with row-level security in Laravel](https://dev.to/addwebsolutionpvtltd/building-multi-tenant-saas-with-row-level-security-in-laravel-3kd3)
- A real project (lms_backend, issue #714, French) hit this collision: `users` is unique on `(email, institution)`, but `password_reset_tokens` keeps `email` as the primary key, so two institutions sharing an address collide. Read through a search summary. — [ouedraogoissouf2012/lms_backend #714](https://github.com/ouedraogoissouf2012/lms_backend/issues/714)

### Inferences
- For the single-table shape (section 1, shape 2), the Postgres DDL would look like this (illustrative):

```sql
-- staff: one account per email platform-wide
CREATE UNIQUE INDEX users_staff_email_unique   ON users (lower(email)) WHERE type <> 'chatter';
-- chatters: one account per email per workspace (owner)
CREATE UNIQUE INDEX users_chatter_email_unique ON users (workspace_id, lower(email)) WHERE type = 'chatter';
```

  For a separate `chatters` table, `$table->unique(['workspace_id', 'email'])` works, but it is case-sensitive. Use a `lower(email)` expression index via `DB::statement`, or normalise email to lowercase on write.
- Chatter sign-in must always pass the tenant key, resolved server-side from the agent (`HostedChatAgent::from($request)` → `$agent->user_id`), never from user input:
  `Auth::guard('chat')->attempt(['workspace_id' => $agent->user_id, 'email' => $email, 'password' => $password])`.
  Without it, with duplicate emails, `->first()` returns an arbitrary row: wrong-account login if the passwords happen to match, and a confusing "invalid credentials" otherwise.
- Staff sign-in on a single table needs the opposite filter (`type <> 'chatter'`). For Fortify, that means `Fortify::authenticateUsing()` (section 4) or a type-filtered provider. Otherwise a chatter whose email matches a staff email can be matched by the dashboard login.
- `retrieveById()` / `retrieveByToken()` (session restore, remember-me) look up by primary key, so they are unaffected by duplicate emails. Only credential-based lookups (login, reset, Socialite/linking code) need the tenant key.
- Keying chatters to the **owner** (`workspace_id` = `$agent->user_id`) matches the CLAUDE.md "key workspace data to the owner" rule. Keying per agent would be finer, but the same person would then need separate credentials for two agents of one workspace.
- The login throttle key (email + IP) is shared across tenants for the same email. This is minor, but a chatter's failed attempts in workspace A count against workspace B. A custom rate-limiter key can include the workspace id.

### Gaps
- I did not find an authoritative stancl/tenancy page on "users that exist per tenant" in single-DB mode. The docs only cover generic unique-index/validation scoping.
- I did not check whether `citext` (case-insensitive text) is a common choice in Laravel/PG apps for this. It is a known PG option but was not researched here.

## 3. Password resets per tenant when the same email exists in two tenants

### Takeaway
Laravel's reset flow has two halves. **User lookup** goes through the broker's provider (`retrieveByCredentials`), so extra credential keys like `workspace_id` pass through. **Token storage** is keyed only by `getEmailForPasswordReset()`, in both the database and the cache repository. Duplicate emails in one broker therefore collide on the token row. Options: a separate broker and table per provider (enough if the duplicates live in *different* providers), overriding `getEmailForPasswordReset()` to return a tenant-unique key, a custom token repository with a tenant column, or skipping passwords for end-users (magic links / OTP). Fortify's reset controllers pass only the email, so a tenant-aware reset outside Fortify's single broker needs custom controllers.

### Cited Findings
- `PasswordBroker::getUser()` does `Arr::except($credentials, ['token'])` and then `$this->users->retrieveByCredentials($credentials)`. Any extra key (for example `workspace_id`) is used in the user lookup. — [PasswordBroker.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/PasswordBroker.php)
- `DatabaseTokenRepository` keys every operation by email: `create()` uses `$user->getEmailForPasswordReset()`; `deleteExisting()` does `where('email', $user->getEmailForPasswordReset())->delete()`; `exists()` and `recentlyCreatedToken()` query `'email', $user->getEmailForPasswordReset()`; `getPayload()` writes `['email' => $email, 'token' => hash, 'created_at' => now]`. There is no tenant column. — [DatabaseTokenRepository.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/DatabaseTokenRepository.php)
- The default `CanResetPassword::getEmailForPasswordReset()` returns `$this->email`. — [CanResetPassword.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/CanResetPassword.php)
- Cache driver (documented in the 13.x docs; the release that added it was not checked): "Entries are keyed by a SHA-256 hash of the user's email address". Config: `'driver' => 'cache', 'provider' => 'users', 'store' => 'passwords', 'expire' => 60, 'throttle' => 60`. The `store` key protects tokens from `cache:clear`. — [Laravel 13 Resetting Passwords](https://laravel.com/docs/13.x/passwords#configuration); `CacheTokenRepository` keys by `hash('sha256', $user->getEmailForPasswordReset())` — [CacheTokenRepository.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/CacheTokenRepository.php)
- "The user provider used by the password broker is configured within the `passwords` configuration array of your `config/auth.php`". — [Laravel 13 Resetting Passwords](https://laravel.com/docs/13.x/passwords#requesting-the-password-reset-link)
- The docs say trusted hosts are "particularly important when your application offers password reset functionality", because absolute URLs are built from the `Host` header. — [Laravel 13 Resetting Passwords: trusted hosts](https://laravel.com/docs/13.x/passwords#configuring-trusted-hosts)
- Reset link customisation: `ResetPassword::createUrlUsing(fn (User $user, string $token) => …)` is a static, app-wide callback that receives the notifiable. Alternatively, override `sendPasswordResetNotification($token)` on the model. — [Laravel 13 Resetting Passwords: customization](https://laravel.com/docs/13.x/passwords#password-customization)
- The default `ResetPassword::resetUrl()` builds `route('password.reset', ['token' => …, 'email' => $notifiable->getEmailForPasswordReset()])`. The single global route name `password.reset` and the reset key both end up in the URL. — [ResetPassword.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Notifications/ResetPassword.php)
- Older (2019) issue: `getEmailForPasswordReset` was "only used when creating or deleting the tokens", and the notification defaulted to the `email` attribute. Closed by driesvints as a feature request. Current code *does* use it in the reset URL, so part of that complaint is outdated. — [laravel/framework #27320](https://github.com/laravel/framework/issues/27320)
- Fortify passes only the email to the broker: `PasswordResetLinkController` calls `$this->broker()->sendResetLink($request->only(Fortify::email()))`; `NewPasswordController` calls `->reset($request->only(Fortify::email(), 'password', 'password_confirmation', 'token'), …)`. Both use `Password::broker(config('fortify.passwords'))`. — [PasswordResetLinkController.php](https://github.com/laravel/fortify/blob/1.x/src/Http/Controllers/PasswordResetLinkController.php); [NewPasswordController.php](https://github.com/laravel/fortify/blob/1.x/src/Http/Controllers/NewPasswordController.php)
- Laracasts (Jan 2025): a Fortify/Jetstream multi-tenant app wanted reset tokens per domain. Proposed schema: `password_reset_tokens` with `domain_id` FK and `unique(['domain_id', 'email'])`. The answer (martinbean): extend the broker with your own implementation and accept the domain id in `$credentials` when creating links and when resetting. No full code was given. — [Laracasts: Customizing Fortify for multi-tenant password reset tokens](https://laracasts.com/discuss/channels/laravel/customizing-fortify-for-multi-tenant-password-resets-tokens-with-domain-specific-tokens)
- lms_backend #714 plan: subclass `DatabaseTokenRepository` and override `deleteExisting`, `exists`, `recentlyCreatedToken` and `getPayload` to add the tenant column; extend `PasswordBrokerManager` and rebind `auth.password`; "about 40 lines". This is a plan, not shipped code. Read through a search summary. — [lms_backend #714](https://github.com/ouedraogoissouf2012/lms_backend/issues/714)
- spatie/laravel-multitenancy discussion #482 (multi-DB): tenant reset tokens landed in the landlord `password_reset_tokens` table. The suggested fix was a per-broker `connection` key in `config/auth.php`. Read through a search summary, not fetched. — [spatie/laravel-multitenancy Discussion #482](https://github.com/spatie/laravel-multitenancy/discussions/482)
- Generic multi-broker tutorials (separate brokers per table, override the broker in controllers) exist but are older. — [DEV: Password brokers on multiple tables](https://dev.to/kaperskyguru/password-brokers-reset-passwords-on-multiple-tables-in-laravel-551g); [DEV: multi-guard reset password API in Laravel 11](https://dev.to/hishamm1/building-a-multi-guard-reset-password-api-in-laravel-11-1khg)
- Laravel's own e-mail verification links use `URL::temporarySignedRoute(...)`, a built-in primitive for signed, expiring links. A magic-link sign-in can reuse it. — [VerifyEmail.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Notifications/VerifyEmail.php)

### Inferences
- **Separate `chatters` broker and table** solves staff-vs-chatter collisions: the same email as owner and chatter goes to different tables. It does **not** by itself solve chatter-vs-chatter collisions across workspaces, because the token table is still keyed by email.
- **Cheapest fix for chatter-vs-chatter:** override `getEmailForPasswordReset()` on the chatter model to return a value that is unique per row (for example the `external_id`, or `"{$workspaceExternalId}|{$email}"`). The token row is then unique per chatter account. Lookup still works because the reset form posts `workspace_id` (resolved from the agent route) + `email` as credentials, and `exists()` recomputes the key from the found user. Two things must follow: (a) `ResetPassword::createUrlUsing()` or a custom `sendPasswordResetNotification()` so the URL does not show that key as `email` and points at the hosted-chat reset page `/chat/{agentSlug}/reset-password/{token}`; (b) the `email` column length/type fits the key. This trick is not documented anywhere I found. It follows from the source above and should be tested.
- **Custom token repository** (a `workspace_id` column plus the overrides listed in #714) is the explicit, self-documenting version. It needs a custom `PasswordBrokerManager` or a broker built by hand in the chatter reset Action.
- **Magic link / one-time code for chatters** avoids per-tenant passwords and resets entirely. It fits a "sign in to chat" surface, where users rarely return with a password. It can use `URL::temporarySignedRoute` scoped to agent and workspace. This is a product decision; no Laravel-specific source compared the two for chat widgets.
- Whichever option is chosen, the chatter reset cannot go through Fortify's controllers (single broker, email-only credentials). It needs its own invokable controllers under `App\Http\Chat`, which matches Chatvia's controller rules.

### Gaps
- I found no first-party Laravel guidance or framework PR for "same email, multiple tenants, one broker". All solutions found are community patterns.
- I did not verify the `connection` broker key in `PasswordBrokerManager::createTokenRepository()` source; only the cache branch was read.
- No first-party Laravel magic-link package exists that I know of. Third-party packages were not researched.

## 4. Fortify is single-guard; Filament per-panel guard/broker; Sanctum with multiple tokenable models

### Takeaway
Fortify binds its whole flow (login, 2FA, reset, verification, passkeys) to one `fortify.guard` and one `fortify.passwords` broker. There is no supported second Fortify instance. Apps keep Fortify for one population and write plain controllers (`Auth::guard('x')->attempt`, `Password::broker('x')`) for the other. Filament panels each take `->authGuard()` and `->authPasswordBroker()`. Sanctum's `auth:sanctum` guard has `provider => null` by default, so it accepts a token from **any** model that uses `HasApiTokens` unless you pin a provider.

### Cited Findings
- Fortify config defaults: `'guard' => 'web'`, `'passwords' => 'users'`, `'username' => 'email'`. — [fortify config](https://github.com/laravel/fortify/blob/1.x/config/fortify.php)
- `FortifyServiceProvider` binds `StatefulGuard` to `Auth::guard(config('fortify.guard', null))`. Its reset controllers use `Password::broker(config('fortify.passwords'))`. — [FortifyServiceProvider.php](https://github.com/laravel/fortify/blob/1.x/src/FortifyServiceProvider.php); [PasswordResetLinkController.php](https://github.com/laravel/fortify/blob/1.x/src/Http/Controllers/PasswordResetLinkController.php)
- Fortify has `Fortify::authenticateUsing(callable)`, to customise how the login request finds and validates the user, and `Fortify::ignoreRoutes()`, to disable Fortify's routes. — [Fortify.php](https://github.com/laravel/fortify/blob/1.x/src/Fortify.php); [Laravel 13 Fortify docs](https://laravel.com/docs/13.x/fortify)
- Fortify issue #29 (Sep 2020) asked for multiple logins with a custom (admin) guard. driesvints replied that it could be contributed as a PR and closed it the same day. No PR is linked. — [laravel/fortify #29](https://github.com/laravel/fortify/issues/29)
- spatie/laravel-multitenancy discussion #389: a developer found Fortify accepts only one guard, so they disabled Fortify's routes and copied login/logout into their own routes. Read through a search summary. — [spatie/laravel-multitenancy Discussion #389](https://github.com/spatie/laravel-multitenancy/discussions/389)
- Older (Fortify 1.7 / Laravel 8): verification routes used plain `auth` middleware instead of the configured guard. Read through a search summary; may be fixed since. — [laravel/fortify #295](https://github.com/laravel/fortify/issues/295)
- Filament 5: each panel takes `->authGuard('web')` and `->authPasswordBroker('users')`, plus per-panel `->login()`, `->passwordReset()`, `->emailVerification()`, `->profile()`. Access is gated by `FilamentUser::canAccessPanel(Panel $panel)`. — [Filament 5 Users overview](https://filamentphp.com/docs/5.x/users/overview)
- Sanctum registers `auth.guards.sanctum` as `['driver' => 'sanctum', 'provider' => null]` merged with app config. `createGuard()` passes `$config['provider']` into `Laravel\Sanctum\Guard`. — [SanctumServiceProvider.php](https://github.com/laravel/sanctum/blob/4.x/src/SanctumServiceProvider.php)
- Sanctum `Guard::__invoke` first loops `config('sanctum.guard', 'web')` session guards and returns any user found there (cookie/SPA auth). Otherwise it reads the bearer token, finds it with `PersonalAccessToken::findToken`, and checks `hasValidProvider($tokenable)`, which **returns true when the provider is null**. Otherwise it requires `$tokenable instanceof config("auth.providers.{provider}.model")`. — [Sanctum Guard.php](https://github.com/laravel/sanctum/blob/4.x/src/Guard.php)
- Sanctum config: "This array contains the authentication guards that will be checked when Sanctum is trying to authenticate a request. If none of these guards are able to authenticate the request, Sanctum will use the bearer token". Default `['web']`. — [sanctum config](https://github.com/laravel/sanctum/blob/4.x/config/sanctum.php)
- Tokens live in one polymorphic table: `personal_access_tokens` uses `$table->morphs('tokenable')`. — [create_personal_access_tokens_table](https://github.com/laravel/sanctum/blob/4.x/database/migrations/2019_12_14_000001_create_personal_access_tokens_table.php)
- The provider check came from a 2020 PR, "Added Multiple Provider Support". — [laravel/sanctum PR #149](https://github.com/laravel/sanctum/pull/149)
- Community pattern: one sanctum-driver guard per model, e.g. `'customer' => ['driver' => 'sanctum', 'provider' => 'customers']`, with `HasApiTokens` on each model and routes protected with `auth:customer`. Blog post, read through a search summary. — [1v0.net: multi-auth API with Laravel & Sanctum](https://1v0.net/blog/how-to-build-a-multi-auth-api-with-laravel-sanctum/)
- Older Sanctum issue: SPA (cookie) auth does not support picking among multiple guards dynamically. — [laravel/sanctum #144](https://github.com/laravel/sanctum/issues/144)

### Inferences
- Recommended split for Chatvia: Fortify stays for staff (`web` guard, `users` broker). Filament keeps its own `admin` guard and `users` broker. Chatters get hand-written invokable controllers (login, logout, forgot, reset, verify) using `Auth::guard('chat')` and `Password::broker('chatters')`. Chatvia already has a separate `chat` guard, so the controllers mostly exist; they need the tenant key added.
- **Sanctum pitfall to close before adding a chatter model:** if the chatter model gets `HasApiTokens`, a chatter token passes `auth:sanctum` on `/api/v1` (staff API) because `provider` is null. Fix it with `'sanctum' => ['driver' => 'sanctum', 'provider' => 'users']` in `config/auth.php`, plus a separate `chatter-api` guard if chatters ever need tokens. In the single-table shape, the instanceof check cannot tell staff from chatters (same class), so the API middleware must also check `type`. Today `api.owner` and the permission middleware probably cover this, but it should be checked.
- `sanctum.guard = ['web']` means Sanctum's stateful (cookie) path only checks the dashboard session. A chatter signed in on the `chat` guard does **not** authenticate through `auth:sanctum`. That is the desired isolation, so do not add `chat` to that list.
- A chatter model needs its own morph alias in the morph map (`getMorphClass()`, never `::class`, per CLAUDE.md) for `personal_access_tokens.tokenable_type`, notifications and activity logs.

### Gaps
- Not verified whether Fortify issue #295 (verification routes ignoring the guard) is fixed in v1.41.
- No official Laravel statement says "a second Fortify instance is unsupported". The conclusion rests on the single-valued config keys and the controllers shown in source.

## 5. Email verification, notifications, Socialite and passkeys for a second authenticatable model

### Takeaway
These all work with a second model, with some setup. `verified` and `EmailVerificationRequest` use `$request->user()`, which follows the guard chosen by `auth:<guard>`. The verification and reset notifications use **global** route names and static URL callbacks, so a second model needs class-aware `createUrlUsing` callbacks or its own notifications. Socialite does not care about guards: you log the model in yourself, and the lookup must include the tenant key. Passkeys are the hard part: `laravel/passkeys` (and Fortify's wrapper) supports one user model and one guard per app.

### Cited Findings
- `Authenticate` middleware: for the first guard whose `check()` passes, it calls `$this->auth->shouldUse($guard)`. `shouldUse()` makes that guard the default and resets the user resolver, so `$request->user()` returns the user of that guard afterwards. — [Authenticate.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Middleware/Authenticate.php); [AuthManager.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/AuthManager.php)
- `EnsureEmailIsVerified` (`verified`) checks `$request->user() instanceof MustVerifyEmail && ! hasVerifiedEmail()` and redirects to `$redirectToRoute ?: 'verification.notice'`. — [EnsureEmailIsVerified.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Middleware/EnsureEmailIsVerified.php)
- `EmailVerificationRequest::authorize()` compares `$this->user()->getKey()` with route `id`, and `sha1($this->user()->getEmailForVerification())` with route `hash`. — [EmailVerificationRequest.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Foundation/Auth/EmailVerificationRequest.php)
- `VerifyEmail::verificationUrl()` uses the static `createUrlUsing` callback if set; otherwise `URL::temporarySignedRoute('verification.verify', now + auth.verification.expire, ['id' => getKey(), 'hash' => sha1(getEmailForVerification())])`. — [VerifyEmail.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Notifications/VerifyEmail.php)
- Password reset requires the model to use `Notifiable` and implement `CanResetPassword`. — [Laravel 13 Resetting Passwords: model preparation](https://laravel.com/docs/13.x/passwords#model-preparation)
- Socialite: after `Socialite::driver('github')->user()`, the docs example does `User::updateOrCreate(['github_id' => $githubUser->id], [...])` and `Auth::login($user)`. Socialite itself has no guard or user-model setting. — [Laravel 13 Socialite](https://laravel.com/docs/13.x/socialite#authentication-and-storage)
- `laravel/passkeys` (v0.2.1 installed; repo `laravel/passkeys-server`): config `'guard' => 'web'`, commented "This should match your application's primary authentication guard". The user model is a single static `Passkeys::$userModel`, set with `Passkeys::useUserModel()`. — [laravel/passkeys-server](https://github.com/laravel/passkeys-server); [Packagist laravel/passkeys](https://packagist.org/packages/laravel/passkeys)
- Fortify wraps it. It sets `passkeys.guard` to `config('fortify.guard')` and resolves the passkey user model from the Fortify guard's provider (`passkeyUserModel()`). — [FortifyServiceProvider.php](https://github.com/laravel/fortify/blob/1.x/src/FortifyServiceProvider.php)
- A third-party write-up says the `PasskeyAuthenticatable` trait assumes `name` and `email` columns on the user table. Unverified. — [DEV: Laravel native passkeys guide](https://dev.to/hafiz619/laravel-now-has-native-passkeys-a-complete-guide-to-laravelpasskeys-4151)
- spatie/laravel-passkeys configures one authenticatable model (an `AUTH_MODEL`-style setting). Read through a search summary. — [spatie/laravel-passkeys installation](https://spatie.be/docs/laravel-passkeys/v1/installation-setup)

### Inferences
- **Verification for chatters:** register chatter routes (for example `chat.verification.notice` / `chat.verification.verify`), guard them with `auth:chat` and `verified:chat.verification.notice`, and use `VerifyEmail::createUrlUsing(fn ($n) => $n instanceof Chatter ? URL::temporarySignedRoute('chat.verification.verify', …) : <default>)`. Or give the chatter model its own `sendEmailVerificationNotification()` and notification. The same applies to `ResetPassword::createUrlUsing`. Both callbacks are app-wide statics, so one callback must branch on the model class. Note: in the single-table shape the class is the same, so branch on `type`.
- **Notifications** need the chatter model to use `Notifiable`. Its `preferredLocale()` should follow the chatter's or agent's language (Chatvia sends e-mail through `User::preferredLocale()`), and the mail should carry the *tenant's* agent branding, not Chatvia's dashboard branding. That second point is a product inference.
- **Socialite for chatters:** store the provider identity per tenant (`unique(workspace_id, provider, provider_user_id)`), look it up with the workspace id, and call `Auth::guard('chat')->login($chatter)`. If the OAuth app (client id) is Chatvia-wide, the same Google account maps to different chatter rows per workspace. That is correct for per-tenant identity.
- **Passkeys for chatters:** not supported side by side with staff passkeys by `laravel/passkeys`/Fortify (one model, one guard). In the separate-model shape, chatter passkeys would need a separate WebAuthn integration (for example `laragear/webauthn`, not researched) or a fork. For an embedded widget, WebAuthn inside a cross-origin iframe needs the embedding page's permission policy; not researched. Passkeys for chatters are probably a later phase.

### Gaps
- Did not research `laragear/webauthn` or other WebAuthn packages for multi-model support.
- Did not research WebAuthn in third-party iframes (`publickey-credentials-get` permissions policy) for the widget surface.

## 6. Session and cookie isolation between the dashboard and the end-user surface on the same domain

### Takeaway
Guards already keep separate *login state* inside one session: each guard has its own session key and remember-me cookie. They still share one session cookie, CSRF token and session id, so `session()->invalidate()` on one surface's logout also logs the other guard out. The `sessions.user_id` column records only the default guard's id. Full isolation needs a different session cookie name/path for the end-user surface, set **before** `StartSession` builds the store. Chatvia already does this for `/chat`.

### Cited Findings
- `SessionGuard::getName()` returns `'login_'.$this->name.'_'.sha1(static::class)`, and `getRecallerName()` returns `'remember_'.$this->name.'_'.sha1(static::class)`. Each guard stores its user id under its own session key and its own remember cookie. — [SessionGuard.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/SessionGuard.php)
- The docs' logout example calls `Auth::logout(); $request->session()->invalidate(); $request->session()->regenerateToken();`. Invalidating the shared session also drops every other guard's login key. — [Laravel 13 Authentication: logging out](https://laravel.com/docs/13.x/authentication#logging-out)
- `SessionManager::buildSession()` creates the `Store` with `$this->config->get('session.cookie')` as its name when the store is built. The cookie name must be changed before the session driver is resolved. — [SessionManager.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Session/SessionManager.php)
- Community confirmation (older): setting `session.cookie` via `config()` mid-request did not rename the cookie. It had to happen in middleware that runs before the session starts. A 2021 blog post shows a middleware that sets both `config('session.cookie')` and the session's name. — [vpalos.com: dynamic session cookie name in Laravel (2021)](https://vpalos.com/2021/09/28/dynamic-session-cookie-name-in-laravel); [Laracasts reply](https://laracasts.com/discuss/replies/878013)
- `DatabaseSessionHandler::addUserInformation()` writes `user_id = $this->container->make(Guard::class)->id()`, the **default** guard's id. With two models, `sessions.user_id` can hold an id from either table. — [DatabaseSessionHandler.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Session/DatabaseSessionHandler.php)
- A developer with admin and user guards in one browser saw the shared `sessions.user_id` flip depending on which side was loaded. Forum report, read through a search summary. — [Laracasts: multiple guards or permissions](https://laracasts.com/discuss/channels/site-improvements/architecture-question-multiple-guards-or-permissions)
- Remember-me cookies named `remember_web_…` collided between two apps on one domain. Forum report, read through a search summary. — [Laracasts reply](https://laracasts.com/discuss/replies/587824)
- stancl/tenancy v3 "session scoping": the `ScopeSessions` middleware returns 403 on attempts to use a session from another tenant. It works "only assuming you use a domain per tenant". With path identification you need DB sessions (multi-DB) or single-DB tenancy. Redis sessions are separated per tenant by `RedisTenancyBootstrapper`. — [Tenancy for Laravel v3: session scoping](https://tenancyforlaravel.com/docs/v3/session-scoping)
- Laravel's session config supports `path`, `same_site` and `partitioned` (CHIPS) options. Chatvia's `config/session.php` already defines a `chat` block with `'path' => '/chat'`, SameSite=None and partitioned cookies for the embed iframe. Source: `config/session.php` (local); framework default config — [laravel/framework config/session.php](https://github.com/laravel/framework/blob/13.x/config/session.php)

### Inferences
- Chatvia's `UseHostedChatSession` (global middleware, runs before the `web` group's `StartSession`, swaps cookie name, path, secure and same_site for `/chat/`) is the standard pattern. A new chatter model needs no new session work, only a change of the `chat` guard's provider.
- After the identity split, add a check that `/chat` routes never resolve the `web` guard and dashboard routes never resolve `chat`. Path-scoped cookies make this true by construction, as long as no `/chat` route is also reachable under a dashboard path.
- With a separate chatter table, Chatvia's sessions table `user_id` for `/chat` requests (default guard = `chat` after `shouldUse`) would hold a **chatter** id in a column read as a `users.id`. "Log out other devices" or session listings in the dashboard could then show the wrong user. Either use a separate session table/connection for the chat session, or accept that `sessions.user_id` is ambiguous and never join it to `users` for chat sessions. The widget uses `X-AUTH-TOKEN` (`WidgetAuthSessionService`), not the Laravel session, so it is not affected.

### Gaps
- Did not find an official Laravel docs section on per-route-group session cookies; the evidence is source code plus older community posts.
- Did not verify the default `config/session.php` URL path in the framework repo for 13.x. Laravel 11+ ships a framework-level default config, which I believe is at that path.
