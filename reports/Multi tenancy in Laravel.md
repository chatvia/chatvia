# Build Laravel Tenancy From Layers, Not Packages

In 2025–2026 Laravel practice, most SaaS apps keep every tenant in **one shared database with a tenant key on each row**, and they protect it with several small layers, not with one package. First-party tools now cover membership. Since March 2026 the official Laravel 13 starter kits can generate teams with a role pivot, invitations and a team slug in the URL, and Filament 5 has panel tenancy. But neither of them scopes your data. Only stancl/tenancy scopes rows automatically, and only its untagged v4 adds PostgreSQL row-level security (RLS), which its own docs call experimental. Global scopes miss raw SQL, validation rules, queue restores and admin paths, so teams add policies, tenant-aware validation, tenant-aware jobs, tenant-scoped indexes and two-tenant tests around them. A tenant's end-users get their own identity space through a separate guard, provider and password broker, because Fortify, Sanctum, passkeys and Laravel's reset tokens all assume one email per table. For Chatvia, the scoping side is mostly right already: one database, data keyed to the owner, a separate admin panel, separate chat sessions, and a signed workspace header for MCP. The weak point is identity. Chatters share the global `users` table, so one email cannot be a chatter in two workspaces, and the owner's user row is also the tenant key. Chatvia is not released and schema changes go into the create migrations, so now is the cheapest time to give workspaces and chatters their own rows.

## Only stancl/tenancy scopes rows; first-party tools stop at membership

stancl/tenancy (archtechx) is still the most used tenancy package, with about **1.03 million installs per month** ([Packagist](https://packagist.org/packages/stancl/tenancy)). Its only tagged line is v3. The latest release, **v3.10.1 from 2026-08-05, supports Laravel 10 to 13** ([Packagist metadata](https://repo.packagist.org/p2/stancl/tenancy.json)). Version 4 lives on the `master` branch and needs PHP 8.4 ([composer.json](https://github.com/archtechx/tenancy/blob/master/composer.json)). Its docs say it was released in 2026 ([v4 introduction](https://v4.tenancyforlaravel.com/introduction/)), but no v4 tag exists on GitHub or Packagist, so using it means pinning `dev-master` ([GitHub tags](https://github.com/archtechx/tenancy/tags)). Small breaking changes were still landing in September and October 2026 ([commits](https://github.com/archtechx/tenancy/commits/master)). The core is MIT. Paid extras sit next to it, and the guides for Filament integration and central sign-in are for sponsors only ([v4 sponsoring](https://v4.tenancyforlaravel.com/sponsoring/)). In single-database mode, a `BelongsToTenant` trait adds an Eloquent global scope, fills the tenant id on create, and the tenant model offers `$tenant->unique()` and `$tenant->exists()` validation helpers ([v4 single-database docs](https://v4.tenancyforlaravel.com/single-database-tenancy/)). The scope itself is about twenty lines. It filters by the tenant key, and it does nothing at all when no tenant is set ([TenantScope.php](https://github.com/archtechx/tenancy/blob/master/src/Database/TenantScope.php)).

spatie/laravel-multitenancy takes the opposite path. Version 4.2.1 (2026-09-22, Laravel 11–13) only finds the current tenant, runs "switch tenant" tasks, and makes queued jobs tenant-aware ([Packagist metadata](https://repo.packagist.org/p2/spatie/laravel-multitenancy.json); [Spatie docs](https://spatie.be/docs/laravel-multitenancy/v4/introduction)). It has **no row scoping**. Its model traits only choose a database connection ([source tree](https://github.com/spatie/laravel-multitenancy/tree/main/src)). Its queue design is the part worth copying. It records the tenant at dispatch, fails a job whose tenant no longer exists, and restores the previous tenant after each job ([Spatie queue docs](https://spatie.be/docs/laravel-multitenancy/v4/basic-usage/making-queues-tenant-aware)).

The first-party news of 2026 is membership, not isolation. Laravel's kit builder merged team support on 2026-03-27 ([laravel/maestro PRs](https://github.com/laravel/maestro/pulls?q=teams)). Since then the React, Svelte, Vue and Livewire starter kits can be generated with teams ([Laravel 13 starter kits](https://laravel.com/docs/13.x/starter-kits)). Each user gets a personal team, a `current_team_id`, and routes under `/{current_team}/…`. A middleware returns 403 when the user is not a member. The kits add no tenant scope to your models. Filament 5 (v5.10.1) also has tenancy, but only inside a panel configured with `->tenant()`. Its docs list the gaps and state plainly: "Filament does not provide any guarantees about the security of your application" ([Filament 5 tenancy](https://filamentphp.com/docs/5.x/users/tenancy)). Jetstream teams are legacy. The Laravel 12 release notes say Jetstream gets no more updates ([Laravel 12 release notes](https://laravel.com/docs/12.x/releases)), although Packagist still shows Laravel 13 compatibility releases ([Packagist metadata](https://repo.packagist.org/p2/laravel/jetstream.json)). spatie/laravel-permission v8 has a teams mode, but it scopes roles and permissions, not data ([teams docs](https://github.com/spatie/laravel-permission/blob/main/docs/basic-usage/teams-permissions.md)).

| Tool (Oct 2026) | Scopes rows for you | Isolation enforced by the database | Membership model | Status |
|---|---|---|---|---|
| stancl/tenancy v3.10.1 | Yes, Eloquent only | No | Not provided | Stable, Laravel 10–13 |
| stancl/tenancy v4 (`dev-master`) | Yes, or RLS instead | Yes, PostgreSQL RLS, called experimental | Not provided (sponsor guide) | No tag, PHP 8.4+ |
| spatie/laravel-multitenancy 4.2.1 | No | No | Not provided | Stable, Laravel 11–13 |

| spatie/laravel-permission teams | No (roles only) | No | Roles per team | v8.3.0 |

So for an existing app, the common practice is to copy patterns, not to adopt a package. Laravel Daily's April 2026 article makes this point. Teams are the base layer. A `team_id` column plus global scopes covers most SaaS apps. Database-level isolation is for compliance and similar needs ([Laravel Daily](https://laraveldaily.com/post/is-the-new-laravel-13-teams-the-same-as-multi-tenancy)). The parts copied most often are stancl's small scope and validation helpers, Spatie's tenant-aware jobs, and the starter kit's membership tables and middleware.

## The tenant is now its own row, and ownership is a role

The 2026 first-party default is **a separate tenant table plus a membership pivot**. In the starter kits' teams option, `teams` has a unique `slug`, an `is_personal` flag and soft deletes. `team_members` holds `team_id`, `user_id` and a `role` string, with `unique(team_id, user_id)`. `team_invitations` has a code and an expiry. `users.current_team_id` is a nullable foreign key that becomes null when its team is deleted ([teams migration](https://github.com/laravel/vue-starter-kit/blob/teams/database/migrations/2026_01_27_000001_create_teams_table.php); [current_team_id migration](https://github.com/laravel/vue-starter-kit/blob/teams/database/migrations/2026_01_27_000002_add_current_team_id_to_users_table.php)). **Ownership is a role, not a column.** A `TeamRole` enum has `owner`, `admin` and `member`, and each role's permissions are a fixed map in PHP, not database rows ([TeamRole.php](https://github.com/laravel/vue-starter-kit/blob/teams/app/Enums/TeamRole.php)). Jetstream, the older default, stored the owner in `teams.user_id`. When a user was deleted, it deleted every team that user owned, with no transfer step ([Jetstream DeleteUserWithTeams](https://github.com/laravel/jetstream/blob/5.x/stubs/app/Actions/Jetstream/DeleteUserWithTeams.php)). Filament 5 assumes a user can belong to many tenants. If a user can only ever be in one tenant, Filament advises skipping its tenancy feature and using a plain column, a global scope and an observer instead ([Filament 5 tenancy](https://filamentphp.com/docs/5.x/users/tenancy)).

The "user is the tenant" model still exists in these designs, but only as the personal team. The trade-offs decide when that is enough. With ownership as a pivot role, moving ownership is one row update. With the owner's user row as the tenant, moving ownership means re-keying every owned row. A tenant row can outlive its owner. When the user is the tenant, deleting the person deletes the business. **Membership in several tenants is the deciding factor.** If one person must ever work in two workspaces, as agency staff and consultants do, only a pivot can express it. Billing follows the same logic: Filament and Spark bill the team, not the user ([Filament 5 tenancy](https://filamentphp.com/docs/5.x/users/tenancy); [Spark cookbook](https://spark.laravel.com/docs/spark-stripe/cookbook)). Other SaaS products use simple transfer rules: one owner at a time, the new owner must already be a member, and billing moves with ownership ([GQueues](https://learn.gqueues.com/en/articles/5315150-transfer-team-ownership); [TeamSnap](https://helpme.teamsnap.com/article/328-transfer-team-ownership)).

The kits read the current tenant from the URL. Routes sit under `/{current_team}/…`. A middleware looks up the slug, returns 403 for non-members, can require a minimum role, and switches `current_team_id` when the URL names a different team. So **the URL wins, and the column only remembers the last team used** ([EnsureTeamMembership.php](https://github.com/laravel/vue-starter-kit/blob/teams/app/Http/Middleware/EnsureTeamMembership.php)). A second middleware sets `URL::defaults()`, so server-side `route()` calls fill in the slug ([SetTeamUrlDefaults.php](https://github.com/laravel/vue-starter-kit/blob/teams/app/Http/Middleware/SetTeamUrlDefaults.php)). Because the slug is the first path segment, the kits reject team names such as `settings`, `login` and `dashboard` ([starter kits docs](https://laravel.com/docs/13.x/starter-kits#teams)). The other choices each have a cost. Keeping the tenant only in `current_team_id`, the Jetstream way, means a switch in one tab changes the tenant in every other tab and device without warning ([Jetstream teams docs](https://jetstream.laravel.com/features/teams.html)). A session value has the same problem and does not exist for API calls. Subdomains give the strongest separation and suit white-label products. But they need cookie-domain work, and Filament's custom-domain mode registers a global `tenant` route pattern that can clash with other routes ([Filament 5 tenancy](https://filamentphp.com/docs/5.x/users/tenancy)). A header such as `X-Tenant` suits APIs, but only if the server checks membership on every request.

Role packages add one more detail. spatie/laravel-permission's teams mode keeps one process-wide team id, set with `setPermissionsTeamId()`. The middleware that sets it must run before `SubstituteBindings`, or users get 404 where 403 is expected. After a switch, the cached `roles` and `permissions` relations must be cleared ([spatie teams docs](https://spatie.be/docs/laravel-permission/v6/basic-usage/teams-permissions)). It scopes one level only, so a workspace with sub-teams must choose which level the package sees. Laravel's own kits avoid this global state by keeping a role enum on the membership pivot ([TeamRole.php](https://github.com/laravel/vue-starter-kit/blob/teams/app/Enums/TeamRole.php)).

## Global scopes are a convenience; isolation takes five layers

Laravel has no multi-tenancy recipe of its own. It documents the building blocks: global scopes, scoped route bindings, policies and validation rules ([Eloquent global scopes](https://laravel.com/docs/13.x/eloquent#global-scopes); [routing](https://laravel.com/docs/13.x/routing#implicit-binding)). The pattern that the packages and Filament point to has five layers. First, a middleware finds the tenant and checks membership before route model binding runs. Second, a `BelongsToTenant`-style trait adds a global scope and fills the tenant id on create. Third, nested routes use scoped bindings, and top-level models go through a policy that compares the tenant and answers with `Response::denyAsNotFound()`, so the record's existence stays hidden ([Laravel 13 authorization](https://laravel.com/docs/13.x/authorization)). Fourth, validation rules get a tenant clause. Fifth, unique indexes include the tenant column, for example `unique(['tenant_id', 'slug'])` ([stancl v4](https://v4.tenancyforlaravel.com/single-database-tenancy/)).

Each layer exists because global scopes have known holes. They do not touch `DB::` queries or raw SQL. Laravel's `unique` and `exists` rules run plain queries, so they skip scopes too ([stancl v4](https://v4.tenancyforlaravel.com/single-database-tenancy/); [Filament 5 tenancy](https://filamentphp.com/docs/5.x/users/tenancy)). `withoutGlobalScopes()` removes the tenant scope along with all others. When a queued job restores a model, Laravel uses `newQueryWithoutScopes()`, so the tenant scope never runs on that re-fetch ([Model.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Database/Eloquent/Model.php)). stancl scopes only queries that list many rows. A single instance you already hold is not checked, and child models are not scoped on direct queries unless you add a second trait ([stancl v4](https://v4.tenancyforlaravel.com/single-database-tenancy/)). Filament's scope does not cover records passed into relation managers, widgets or modal table selects ([Filament 5 tenancy](https://filamentphp.com/docs/5.x/users/tenancy)). A scope on `User` that reads `auth()->user()` calls itself in a loop ([Laracasts](https://laracasts.com/discuss/channels/eloquent/using-data-from-authuser-in-global-scope)). Global scopes are also stored statically, so under Octane they can carry over from one request to the next ([laravel/framework PR #46922](https://github.com/laravel/framework/pull/46922)).

The most important design choice is what happens when no tenant is set. stancl applies no filter, which is how its central admin panel sees every row ([stancl v3](https://tenancyforlaravel.com/docs/v3/single-database-tenancy)). That design **fails open**: a forgotten tenant shows all rows. An older Laravel Daily trait adds its scope only if `auth()->check()` passes when the model boots ([Laravel Daily](https://laraveldaily.com/post/simple-laravel-multi-tenancy-with-single-trait)). Models boot once per PHP process. In a Horizon worker nobody is logged in, so the scope is never added for the life of that worker. The safer design **fails closed**. It reads the tenant inside `apply()`, throws when the tenant is missing, and keeps the current tenant in a `scoped()` container binding, which Laravel resets for every request and every queued job ([container docs](https://laravel.com/docs/13.x/container#binding-scoped)).

Two smaller points complete the picture. A hand-written `where('tenant_id', …)->orWhere(…)` can leak rows because of SQL operator order ([Infosec Write-ups](https://infosecwriteups.com/the-orwhere-trap-how-sql-operator-precedence-breaks-multi-tenant-data-isolation-in-laravel-ec598f5a0f27)). A tenant filter applied as a global scope is safe from this, because Laravel wraps existing `or` conditions in a group before it adds the scope ([Builder.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Database/Eloquent/Builder.php)). Platform admins are the other risk. A `Gate::before` that returns `true` for admins skips every policy, tenant checks included ([Laravel 13 authorization](https://laravel.com/docs/13.x/authorization)). The usual Filament answer is a separate admin panel with no tenancy. When support staff must act as a customer, impersonation keeps the normal tenant checks in place. lab404/laravel-impersonate allows everyone to impersonate and be impersonated until you override two methods, and its start and stop events are the place to write an audit record ([laravel-impersonate](https://github.com/404labfr/laravel-impersonate)). Sanctum tokens belong to a user, not a tenant. `tokenCan()` always returns true for first-party SPA requests, so policies must check ownership as well as token abilities ([Sanctum docs](https://laravel.com/docs/13.x/sanctum#token-abilities)).

## End-users need their own identity space, not only their own session

Laravel splits authentication into three parts. A **guard** decides how a request is authenticated. A **provider** decides which table the user comes from. A **password broker** is tied to exactly one provider ([Laravel 13 authentication](https://laravel.com/docs/13.x/authentication); [PasswordBrokerManager.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/PasswordBrokerManager.php)). Apps that serve both staff and customers use this to keep two identity spaces. Bagisto, a Laravel e-commerce platform, has a `customer` guard, provider, model, table and reset flow next to a matching `admin` set ([Bagisto](https://bagisto.com/en/bagisto-multi-guard-authentication/)). Forum advice to use one users table with roles is about different roles of the same people. It is not about end-users who need a separate account in each tenant ([Laracasts](https://laracasts.com/discuss/channels/site-improvements/architecture-question-multiple-guards-or-permissions)).

When one email must be able to exist once per tenant, two shapes work. The first is a **separate model and table** for end-users, with `unique(tenant_id, email)` and its own provider, guard and broker. The second **keeps one table** and replaces the global unique index with two partial unique indexes: one for staff across the platform, and one per tenant for end-users. PostgreSQL supports partial unique indexes directly ([PostgreSQL partial indexes](https://www.postgresql.org/docs/current/indexes-partial.html)), but Laravel's schema builder has no option for the `WHERE` part, so it needs a raw statement ([IndexDefinition.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Database/Schema/IndexDefinition.php)). The single-table shape is the smaller migration but the riskier result. `EloquentUserProvider::retrieveByCredentials()` turns every non-password credential into a `where` and returns `->first()` ([EloquentUserProvider.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/EloquentUserProvider.php)). If any login, reset, social-login or validation path forgets the tenant key, it gets an arbitrary row with that email. A provider can be limited with its `withQuery()` hook, but every path must use it. A third shape, one global identity plus membership, cannot give the same person separate credentials per tenant at all.

Password resets are the part teams miss most. The broker finds the user through its provider, so an extra `tenant_id` credential works for the lookup ([PasswordBroker.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/PasswordBroker.php)). But **the token store is keyed only by email**. That is true for the database repository and for the cache repository, which hashes the email ([DatabaseTokenRepository.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/DatabaseTokenRepository.php); [CacheTokenRepository.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Passwords/CacheTokenRepository.php)). Two accounts with the same email in one broker share one token row. A real project hit exactly this: users were unique per institution, but `password_reset_tokens` still used `email` as its primary key ([lms_backend #714](https://github.com/ouedraogoissouf2012/lms_backend/issues/714)). A separate broker and token table per provider fixes clashes between staff and customers. Clashes between customers of different tenants need more: a tenant column in the token table, a reset key that is unique per account, or no passwords at all, using magic links built on `URL::temporarySignedRoute()` ([Laracasts](https://laracasts.com/discuss/channels/laravel/customizing-fortify-for-multi-tenant-password-resets-tokens-with-domain-specific-tokens); [VerifyEmail.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/Notifications/VerifyEmail.php)).

Most auth packages assume one user population. Fortify ties login, two-factor, reset, verification and passkeys to one `fortify.guard` and one broker, and its reset controllers pass only the email ([FortifyServiceProvider.php](https://github.com/laravel/fortify/blob/1.x/src/FortifyServiceProvider.php); [PasswordResetLinkController.php](https://github.com/laravel/fortify/blob/1.x/src/Http/Controllers/PasswordResetLinkController.php)). The usual answer is to keep Fortify for staff and write plain controllers for end-users ([spatie discussion #389](https://github.com/spatie/laravel-multitenancy/discussions/389)). Filament takes one guard and one broker per panel ([Filament users overview](https://filamentphp.com/docs/5.x/users/overview)). **Sanctum is the hidden trap.** Its guard's provider is `null` by default, and with a null provider it accepts a token from any model that uses `HasApiTokens` ([SanctumServiceProvider.php](https://github.com/laravel/sanctum/blob/4.x/src/SanctumServiceProvider.php); [Sanctum Guard.php](https://github.com/laravel/sanctum/blob/4.x/src/Guard.php)). If you add `HasApiTokens` to a customer model and do not pin the provider, customer tokens pass staff API routes. `laravel/passkeys` supports one user model and one guard per app, so passkeys for end-users need a separate integration ([laravel/passkeys-server](https://github.com/laravel/passkeys-server)). The default login throttle key is email plus IP, so failed logins in one tenant count against the same email in another tenant unless the key includes the tenant ([Laravel 13 authentication](https://laravel.com/docs/13.x/authentication#login-throttling)).

Sessions are a separate problem from identity. Each guard stores its login under its own session key, but all guards share one session cookie, one CSRF token and one session id ([SessionGuard.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Auth/SessionGuard.php)). Calling `session()->invalidate()` on logout from one surface logs the user out of the other too. Full separation needs a different cookie name or path, set before `StartSession` builds the session ([SessionManager.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Session/SessionManager.php)). With the database session driver, `sessions.user_id` stores only the default guard's id, so with two user tables that column can hold ids from either table ([DatabaseSessionHandler.php](https://github.com/laravel/framework/blob/13.x/src/Illuminate/Session/DatabaseSessionHandler.php)).

## One shared PostgreSQL database stays the default; RLS is an optional extra check

The cloud architecture guides agree on the default. AWS calls the shared model "pool" and the dedicated model "silo" ([AWS SaaS Lens](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/silo-pool-and-bridge-models.html)). Azure's 2026 guide says a shared database fits the most tenants per server at the lowest cost, with one database to back up and secure. Its costs are noisy neighbours, a harder restore of one tenant, and no per-tenant keys or regions ([Azure storage and data](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)). Azure recommends a hybrid: a shared database for most tenants, and a dedicated deployment for tenants who pay more or have unusual needs. Database-per-tenant multiplies migrations and connections, and Azure warns that without automation the work becomes unmanageable. Schema-per-tenant on PostgreSQL has a known scale limit. Old mailing-list reports describe `pg_dump` taking **more than 24 hours at over 20,000 schemas** ([pgsql-performance thread](https://www.postgrespro.com/list/thread-id/1803078)), and Heroku warns about lock-memory errors with very many tables ([Heroku](https://help.heroku.com/EW2G2AF7/how-can-i-resolve-the-error-error-out-of-shared-memory-hint-you-might-need-to-increase-max_locks_per_transaction)). These reports are from old PostgreSQL versions, and I found no modern benchmark. stancl describes the Laravel view this way: single-database mode means less operations work and more code work than multi-database mode ([stancl v3](https://tenancyforlaravel.com/docs/v3/single-database-tenancy)).

PostgreSQL row-level security is the only mechanism that also covers raw SQL. With RLS on, a table that has no policy shows no rows ([PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). Superusers and roles with `BYPASSRLS` always skip it. Table owners skip it too, unless the table uses `FORCE ROW LEVEL SECURITY`. A policy without `WITH CHECK` reuses its `USING` clause for writes. Unique and foreign-key checks ignore RLS, so a uniqueness error can still reveal that another tenant holds a value. The standard pattern is one shared application login plus a tenant setting read with `current_setting('app.tenant_id', true)`, not one database role per tenant ([AWS RLS blog, 2020](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/); [Crunchy Data, 2024](https://www.crunchydata.com/blog/row-level-security-for-tenants-in-postgres)).

The hard part is setting the tenant safely. A plain `SET` lasts for the whole connection, so a reused connection can carry one tenant into the next request. PgBouncer's transaction mode does not support `SET` at all ([PgBouncer features](https://www.pgbouncer.org/features.html)). The 2026 Laravel write-ups use `select set_config('app.current_tenant_id', ?, true)` inside a transaction. It acts like `SET LOCAL` but accepts a bound value, and a job middleware sets it again for each queued job ([phpconference.com, 2026](https://phpconference.com/blog/software-architecture/postgresql-row-level-security-multi-tenancy/); [leojeremy/laravel-postgres-rls](https://github.com/leojeremy/laravel-postgres-rls)). stancl v4 takes a different route. Its bootstrapper switches to a dedicated RLS database user and runs a session-level `SET` ([PostgresRLSBootstrapper.php](https://github.com/archtechx/tenancy/blob/master/src/Bootstrappers/PostgresRLSBootstrapper.php)). Its docs call RLS somewhat experimental, require you to drop policies before you alter a table, and require `tenants:rls` after every migration ([stancl v4 RLS](https://v4.tenancyforlaravel.com/postgres-rls/)). The newest dedicated package, leojeremy/laravel-postgres-rls, is tested on PostgreSQL 18 and Laravel 13 and has a useful `rls:audit` command, but it had no releases and no stars when checked ([GitHub](https://github.com/leojeremy/laravel-postgres-rls)).

The sources disagree on whether RLS should replace app-level scoping. The phpconference article says global scopes become unnecessary ([phpconference.com](https://phpconference.com/blog/software-architecture/postgresql-row-level-security-multi-tenancy/)). The leojeremy package limits its promise to application bugs and excludes SQL injection. Azure notes that many multitenant products skip RLS because it is hard to design, test and maintain ([Azure storage and data](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/storage-data)). On speed, PostgreSQL and Supabase both say the best policy compares a value in the row itself, and that the column must lead an index ([PostgreSQL RLS](https://www.postgresql.org/docs/current/ddl-rowsecurity.html); [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)). Policies that follow foreign keys through sub-selects, which stancl's `TableRLSManager` generates, can be slow ([stancl v4 RLS](https://v4.tenancyforlaravel.com/postgres-rls/)). The only claim of no extra cost rests on one query plan, not a benchmark. My reading: **RLS is worth it as a second check under explicit app scoping**, on tables that carry the tenant id directly. It turns a leak into an empty result. That is a safer failure, but a quieter one.

Two PostgreSQL details matter for AI apps. Approximate vector indexes filter after the index scan, so a narrow tenant filter can return far fewer rows than requested ([pgvector README](https://github.com/pgvector/pgvector)). pgvector 0.8 adds iterative scans to fix this. VectorChord's `vchordrq.prefilter` checks the filter before it computes distances. On its test data it raised queries per second by **about 200% at 1% selectivity**, which is the typical shape of a per-tenant filter ([VectorChord prefilter](https://docs.vectorchord.ai/vectorchord/usage/prefilter.html)). I found no documentation on how an RLS policy affects these index scans. Partitioning by tenant only helps for very large tables. PostgreSQL advises a fixed number of `HASH` partitions over one `LIST` partition per customer, because query planning slows down past a few thousand partitions ([PostgreSQL partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)).

## Most real leaks happen outside the normal request

Queue workers do not run HTTP middleware, so the tenant must travel with the job. Laravel's `Context` captures its data when a job is dispatched and restores it while the job runs, and `Context::addHidden()` keeps a value out of the logs ([Laravel 13 Context](https://laravel.com/docs/13.x/context)). The data goes into the job payload and is restored on `JobProcessing` ([ContextServiceProvider.php](https://raw.githubusercontent.com/laravel/framework/13.x/src/Illuminate/Log/Context/ContextServiceProvider.php)). Scoped container bindings are reset for each job, but singletons are not. A per-tenant service bound as a singleton can therefore carry one tenant's state into the next job ([container docs](https://laravel.com/docs/13.x/container#binding-scoped); [Octane docs](https://laravel.com/docs/13.x/octane#dependency-injection-and-octane)). Spatie fails a tenant-aware job when its tenant is gone, and restores the previous tenant afterwards, which matters for `dispatchSync()` ([Spatie queue docs](https://spatie.be/docs/laravel-multitenancy/v4/basic-usage/making-queues-tenant-aware)). stancl advises against mixing central and tenant jobs on one queue connection, because leftover state can make a central job act inside the previous tenant ([stancl v3 queues](https://tenancyforlaravel.com/docs/v3/queues)). Scheduled commands, batch callbacks and closures have no dispatching request, so they must set the tenant themselves.

Laravel scopes no cache key, Redis key, file path or broadcast channel by tenant. Cache tags do not work on the `database` driver, which is Laravel's default, and `Cache::flush()` ignores the key prefix and removes everything ([Laravel 13 cache](https://laravel.com/docs/13.x/cache)). The best-known shared-state leak is OpenAI's in March 2023. A redis-py bug let a cancelled request leave data on a pooled connection, and billing details of about **1.2% of active ChatGPT Plus subscribers** may have been visible to other users. OpenAI's fix added checks that cached data belongs to the user who asked for it ([Help Net Security](https://www.helpnetsecurity.com/2023/03/27/chatgpt-data-leak/)). For broadcasting, anyone can join a public channel. Channel model binding is not scoped the way HTTP binding can be, so every private-channel callback must compare the owner itself ([Laravel 13 broadcasting](https://laravel.com/docs/13.x/broadcasting)).

The 2026 Laravel advisories show one repeated bug: the UI limits a list, but the server does not. In Filament's `AttachAction` and `AssociateAction`, the options were scoped but validation was not, so an edited Livewire request could submit an out-of-scope record. It was fixed in filament/actions 5.6.4 (GHSA-7q3w-xqjw-g3cr, CVE-2026-48067) ([GitHub advisory](https://github.com/advisories/GHSA-7q3w-xqjw-g3cr)). The Curator media plugin let users in multitenant panels find other tenants' media metadata through its picker search ([filament-curator v3.7.8](https://newreleases.io/project/github/awcodes/filament-curator/release/v3.7.8)). The largest recent tenant incident was outside Laravel, on an AI surface. A flawed tenant check in Asana's new MCP server exposed data across organizations. Asana turned MCP off from June 5 to 17, 2025 and notified **about 1,000 customers** ([UpGuard](https://upguard.com/blog/asana-discloses-data-exposure-bug-in-mcp-server)).

Experienced teams test isolation directly. OWASP's top API risk, broken object level authorization, asks for an authorization check in every function that takes a record id from the client. It treats unguessable ids as an extra, not a replacement, and asks for authorization tests that block a deployment when they fail ([OWASP API1:2023](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization)). In Laravel practice this means two-tenant feature tests: act as tenant B, request tenant A's ids, and expect 404 with no data. The same tests apply to jobs, channel callbacks and MCP tools. Architecture tests then ban unscoped `DB::table`, `withoutGlobalScopes()` and bare `exists` rules outside an allow-list. Composite foreign keys such as `FOREIGN KEY (tenant_id, parent_id) REFERENCES parent (tenant_id, id)` make a cross-tenant child row impossible in the database itself ([dev.to schema example](https://dev.to/ahmet_gedik778845/building-a-multi-tenant-video-platform-schema-that-scales-in-postgresql-53dn)). I found no ready-made PHPStan rule for tenant scoping.

## Conclusion

Two points stand out across the sources. First, in 2026 the hard part of Laravel tenancy is no longer finding the current tenant. The starter kits and Filament now handle that. The hard part is the many paths that skip the normal request: jobs, raw SQL, validation, caches, sockets and, now, AI tool calls. Every serious recent leak sat on one of those paths. Second, identity is part of tenancy. Fortify, Sanctum, password brokers and passkeys all assume one email per table. An app whose tenants have their own end-users needs a second identity space, and a single table with a type column does not give one cheaply.

So tenancy is first a decision about rows and keys, and only then a choice of package. When the tenant row, the tenant column on each owned table and the identity tables are right, the enforcement layers become simple and testable. When they are wrong, no package or policy fully covers the gap. RLS is a good second check, but a poor first one.

## What this means for Chatvia

### Chatvia already gets most of the scoping right

Chatvia follows the pooled model the guides recommend. All workspaces share one PostgreSQL 18 database. Owned tables carry the owner's `users.id`: for example `agents.user_id`, `chunks.user_id`, `source_files.user_id` with `unique(user_id, checksum)`, and `mcp_servers.user_id` with `unique(user_id, slug)`. Code finds the owner with `$user->workspace()`, which returns the `users.workspace_id` parent or the user itself (`src/App/Identity/Workspace/Concerns/ResolvesWorkspaceHierarchy.php`). There are no global scopes in `src/`. Scoping is explicit in Actions, in route middleware (`can.access.agent`, `agent.permission:…`, `team.permission:…`) and in the `ConventionsTest` rule for scoped `external_id` lookups. There is no `Gate::before`. The Filament panel has its own `admin` guard and no tenancy, which is the separate-panel pattern. The hosted chat has its own `chat` guard and a `/chat` session cookie set before the session starts, so session isolation is done. Broadcast channels use external ids and the `access-agent` gate (`routes/channels.php`). The internal MCP workspace mode accepts `X-Chatvia-Workspace-Id` only when it is HMAC-signed (`src/App/Http/Middleware/Auth/VerifyInternalMcpRequest.php`), which avoids the Asana bug class. Filament 5.10.1 is past the GHSA-7q3w fix. On database strategy, the self-hosted Docker install already is the "dedicated deployment" option from the Azure hybrid advice. The hosted service does not need database-per-tenant or schema-per-tenant, which would multiply extension installs, migrations, Horizon and Reverb connections, and embedding-storage locks.

### The weak point is identity, and the tenant key has two meanings

All four kinds of people live in one `users` table. It has a `type` enum (`admin`, `workspace`, `employee`, `chatter`) and a **globally unique `email`** (`database/migrations/0001_01_01_000000_create_users_table.php`). The three guards `web`, `chat` and `admin` all read the same `users` provider, and there is one password broker (`config/auth.php`). The hosted-chat password login finds the account with `User::query()->where('email', $email)->first()` and only then checks the type and agent access (`PasswordAuthenticator`, `LoginUserToAgentAction`). Chatter resets go through the default broker by email (`SendChatterPasswordResetLink`). The chat login throttle key is email plus IP (`LoginRequest::throttleKey()`). Four product limits follow. One email cannot be a chatter in two workspaces. A person cannot be staff in one workspace and a chatter in another with the same email. A teammate belongs to exactly one workspace through `users.workspace_id`. And the workspace is the owner's user row, so ownership cannot move, and deleting the owner deletes the workspace.

There is also a quieter problem. The column name `user_id` means "the tenant" on `agents`, `chunks` and `source_files`, but "the person chatting" on `chat_sessions`. `chat_conversations` and `chat_messages` have no owner column at all and reach the owner only through `agent_id` and `chat_conversation_id`. This double meaning makes it hard to write one clear scoping rule, one architecture test, or one RLS policy.

### Recommended data model: a workspace row, staff-only users, and a separate chatters table

I recommend the shape that first-party Laravel now uses, adapted to Chatvia's rules (pivots without timestamps, owner-keyed data, external ids, edits to create migrations).

| Table | What it holds | Key rules |
|---|---|---|
| `workspaces` (new) | The tenant: `external_id`, name, account-wide settings | Every owned table points here; storage prefix becomes `workspaces/{external_id}/…` |
| `workspace_user` (new pivot) | Staff membership: `workspace_id`, `user_id`, `role` enum (`owner`, `member`) | No timestamps; primary key `(workspace_id, user_id)`; the Action keeps at least one owner; a unique index on `user_id` keeps "one workspace per person" until you decide otherwise |
| `users` | Staff only: platform admins, owners, teammates | Unique on `lower(email)`; Fortify, Filament, Sanctum and passkeys stay here; `type` shrinks to admin or staff; `users.workspace_id` goes away |
| `teams` | Sub-teams inside a workspace (same purpose as today) | `teams.user_id` becomes `teams.workspace_id`; spatie teams mode stays on `team_id` |
| `chatters` (new) | A workspace's end-users: `workspace_id`, `external_id`, name, email, password, `email_verified_at`, `locale`, `deactivated_at` | Unique on `(workspace_id, lower(email))`; own provider, the `chat` guard, a `chatters` broker; own morph alias |
| `agent_chatter` (replaces `agent_user`) | Which agents a chatter may use | Composite foreign keys, so a chatter can only be linked to an agent in the same workspace |
| `chatter_password_reset_tokens` (new) | Chatter reset tokens | Keyed by chatter (or by `(workspace_id, email)`), never by email alone |
| Owned tables (`agents`, `chunks`, `source_files`, `mcp_servers`, … plus `chat_conversations`, `chat_messages`, `form_submissions`) | Workspace data | `workspace_id` foreign key to `workspaces`; unique indexes include `workspace_id`; parents get `unique(workspace_id, id)` for composite foreign keys |

Two existing tables change shape. `chat_sessions` gets a nullable `chatter_id` next to its nullable `user_id` (staff), with a CHECK that at most one is set. `message_limits` splits its single `user_id` into a workspace limit and a chatter limit. Chatters should be keyed to the workspace, not to one agent, so one login works for every agent the workspace grants. This matches the standing rule to key data to the owner. Keeping a membership pivot even while each person has one workspace costs little now and turns multi-workspace support into a single index drop later.

### Recommended enforcement: keep explicit scoping, add the missing layers, and add RLS last

Keep explicit scoping as the main gate, rather than adding global scopes. Chatvia passes the owner through DTOs into Actions and jobs. The research shows this is the safer pattern for queues, because restored models skip global scopes and workers run no HTTP middleware. A global scope would need a "current workspace" set at every entry point: dashboard, API, hosted chat, widget, six channel webhooks, MCP servers, Horizon jobs, the scheduler and Reverb. A scope that fails open protects little there. A scope that fails closed breaks every entry point that forgets to set it.

Add the missing layers around the explicit scoping instead. First, never take `workspace_id` from input: Actions set it from the resolved workspace, and it stays out of `$fillable` and request DTOs. Second, add a small tenant-aware rule helper that wraps `Rule::exists()` and `Rule::unique()` with `->where('workspace_id', …)`, and add an architecture ratchet that bans bare `exists:` and `Rule::exists(` in FormRequests. This is the Filament GHSA-7q3w bug class, and every Vue picker for agents, sources, tools, forms and teammates is exposed to it. Third, start every policy method with an owner check that returns `denyAsNotFound()`, without logging the denial, as the standing rule requires. Fourth, add composite foreign keys on cross-table links while the create migrations are still editable. Fifth, carry the workspace id in every job DTO and re-check ownership in the Action. Add `Context::addHidden('workspace_id', …)` in middleware as a safety net, and bind every per-workspace service with `scoped()`, never `singleton()`. Sixth, build every cache key for chat memory and other per-workspace values through one helper that includes the workspace or session id, and check the owner when reading. Never call `Cache::flush()`, because production Redis is shared with other apps. Seventh, make the two-workspace test matrix a CI gate. Generate it from the route list, and add MCP tools, channel callbacks and jobs.

Add PostgreSQL RLS only after those steps, and only on the highest-risk tables (`chunks`, `chat_conversations`, `chat_messages`, `form_submissions`, `source_files`). Use direct `workspace_id` policies, an app role that is neither owner nor `BYPASSRLS`, `FORCE ROW LEVEL SECURITY`, and a separate owner role for migrations and `pg_dump`. Platform work (Filament, account analytics, maintenance commands) needs either a `BYPASSRLS` role or an explicit platform policy. Set the tenant with `set_config(..., true)` inside short transactions, not one transaction per request. A request-long transaction would stay open for a whole LLM stream. Horizon and Reverb need the setting reset for every job.

### Ordered steps

| Step | What to do | Why at this point |
|---|---|---|
| 1 | Settle the open decisions below in plan mode, and write the rename plan for models, tables, morph aliases and route names | These are cross-cutting renames that the standing rules say must not happen without a plan |
| 2 | Write two-workspace isolation tests and architecture ratchets against today's code: routes, FormRequest id fields, channel callbacks, MCP tools, jobs | They protect every later step, and they will catch regressions during the re-keying |
| 3 | Close the cheap gaps: add a `sanctum` guard with `'provider' => 'users'` in `config/auth.php`; add the agent's workspace to the chat login throttle key; add the cache-key helper; add the tenant-aware rule helper and its ratchet | None of these depend on new tables, and the Sanctum fix must exist before any second tokenable model does |
| 4 | Add `workspaces` and `workspace_user`; change owned tables from `user_id` to `workspace_id` in their create migrations; add `workspace_id` to `chat_conversations` and `chat_messages`; add workspace-scoped unique indexes and composite foreign keys in the same pass; move `message_limits`, the storage prefix, the MCP workspace header, AI usage attribution and the Filament `WorkspaceResource` to the new row | The largest change, and the cheapest it will ever be while the app is unreleased |
| 5 | Split chatters: add the `chatters` table, model, provider and broker, and point the `chat` guard at it; rewrite chat password login, magic link, reset, verification and widget-token lookups so they always pass the workspace taken from the agent; add `agent_chatter`, the `chat_sessions.chatter_id` column and the morph alias; update the `/api/v1` chatter endpoints and the `chat.{conversationId}` channel callback, which today accepts only `User` | This solves the stated identity problem; the lookup key always comes from `HostedChatAgent::from($request)`, never from user input |

| 7 | Measure, then decide on RLS for the five high-risk tables: check query plans on `chunks` vector and BM25 search with the retrieval eval harness, and add the two database roles to the Docker installer | RLS needs the direct `workspace_id` column from step 4, and its effect on VectorChord index scans is undocumented |

### Open decisions

| Decision | Options | Recommendation and what it depends on |
|---|---|---|
| Give the workspace its own row? | Yes / keep the owner's user row as the tenant and only split chatters | Yes. It changes the standing rule "key workspace data to the owner" to "key it to the workspace", so the owner must approve that change explicitly |
| Can one staff person join several workspaces? | No for now / Yes | Start with No, enforced by the unique index on `workspace_user.user_id`. If Yes later: take the workspace from the resource in the URL (agent external id → workspace) on agent pages, and use a URL slug or `current_workspace_id` only for workspace-wide pages, given the multi-tab risk |
| Separate `chatters` table or one table with partial indexes? | Separate table / `users` with two partial unique indexes and type-filtered providers | Separate table. The single table is a smaller change, but any lookup path that forgets the filter returns an arbitrary row |
| How do chatters sign in? | Password with per-workspace reset / magic link or one-time code only | Product call. `ChatMagicLinkController` already exists. Magic-link-only removes per-tenant reset tokens entirely |
| Chatter scope | Per workspace / per agent | Per workspace, so one login covers every agent the workspace grants |
| Hosted-chat sessions in the `sessions` table | Shared table, accepting that `user_id` may hold a chatter id / a separate table or connection for `/chat` | With the default `database` driver, a shared table makes `sessions.user_id` ambiguous. Never join it to `users` for chat sessions, or give `/chat` its own table |
| PostgreSQL RLS | Never / later on five tables / broadly | Later, on five tables, after step 4. Self-hosted installs would then need two database roles, which works against the "simple for newcomers" goal |
| Case-insensitive email | `lower(email)` expression indexes / the `citext` type | Either works on PostgreSQL 18. `lower(email)` needs no extension but needs a raw migration statement |
